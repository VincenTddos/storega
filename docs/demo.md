# 期中展示腳本（約 6 分鐘）

照這個順序講，每一步都有「要點哪裡」和「要說什麼」。沒有硬體也能完整展示；有硬體就在第 5 步換成真的板子。

## 0. 展示前（5 分鐘準備）

- 打開 `dashboard/index.html`（或 `cd tools && npm run demo` 後開 http://localhost:8080）。
- 第一次打開會問模式：沒有硬體就選 **展示模式**（之後右上角也能切）。
- 右上角「展示模式」→ 速度選 **10×**，情境選 **正常營運**。
- 「設定 → 門市資訊」填好門市名稱與組員名字。
- 按 `T` 確認日夜模式都正常；投影機偏暗時用夜間模式。
- 把「設定 → 通知 → 告警聲」打開，讓台下聽得到告警。

## 1. 問題（30 秒）· 總覽頁

> 實體店不知道「現在店裡幾個人、大家在哪一區、逛了多久、有多少人買單」，人一多也沒有辦法自動限流。網站有 Google Analytics，實體店沒有——StoreGA 就是實體店的 GA。

指著大數字、近 90 分鐘曲線（虛線是昨天）、四區平面圖、四張指標卡。

## 2. 三種感測器各司其職（1 分鐘）· 分析 → Wi-Fi 準確度

> 入口兩組紅外線判斷方向，算出準確的場內人數，但不知道人在哪；
> 四區的 ESP32 監聽手機的 Wi-Fi 封包，知道大概在哪區，但會多算；
> 毫米波雷達確認區內到底有沒有人。
> 用入口的準確人數去校正 Wi-Fi，得到係數 k，誤差從 70% 降到 10% 左右。

指著「原始誤差 → 校正後誤差 → 誤差下降」三個數字和兩條線。

## 3. 即時店況與回放（1 分鐘）· 即時店況

- 拖曳旋轉 3D 店面，點「服飾區」看細節。
- 右側入口面板：七段顯示器、燈條顏色就是實體板子上的樣子。
- 拖時間軸回到中午尖峰，說「每一分鐘都可以回放」，按 `Esc` 回到即時。

## 4. 自動限流（1 分鐘）· 模擬器 → 人潮湧入

> 人一多，入口板子自己會關閘門——就算網路斷了也照樣限流。

切到 **人潮湧入**（60× 更快），等大數字卡片邊緣亮起光束、出現「已達上限」告警與告警聲、燈條轉紅、門外開始排隊。再示範「按住 1.5 秒緊急關閉閘門」。

## 5. 真的是 MQTT（1 分鐘）· 裝置頁下方「MQTT 訊息」

> 每一則都是板子送出的 JSON，主題是 `sga/節點/類型`。

- 點一則展開 JSON。
- 點「閃燈」，主控台出現一則「指令」；有硬體時板子的 LED 會閃。
- 切 **節點故障** 情境：zone-B 15 秒後判定離線，點「需要處理」的「重新開機」看整個流程。

有硬體時：右上角 → 切換到真實模式 → 輸入 `ws://<Node-RED 電腦 IP>:8080` → 連線。真實模式只顯示板子真的送來的資料，數字從現在開始累積，重新整理也會接續。

最後打開 **日誌** 頁：每一次連線、節點上線／斷線、閘門開關、告警與剛剛按過的按鈕都在這裡，可以匯出 `.log`。

## 5.5 它可靠嗎？（1 分鐘）· 裝置頁、分析 → 現場驗證

> 每則訊息都有序號和時間，所以我們量得到延遲和掉了幾則；指令送出去，板子會回覆「已執行」或「拒絕」。

- 裝置頁：指著「延遲」「遺失」兩欄，點 entry-01 看「最近指令：已確認 __ ms」。
- 分析 → 現場驗證：秀出之前在門口人工計數的結果——「紅外線準確度 __%，抽查 __ 次」。
- 有時間的話在終端機跑 `npm run security-check`：沒有密碼的人連不上，也不能開閘門。

## 6. 隱私與工程細節（30 秒）· 設定 → 韌體設定

> MAC 在板子上就先加鹽做 SHA-256，只留前 8 bytes、60 秒後就丟；員工手機用雜湊白名單排除。這頁可以直接產生每塊板子要燒的 `config.h`。

## 7. 收尾（30 秒）

> 韌體、Node-RED、儀表板都有自動測試，GitHub 每次推送都會跑一遍。

可以順手按「分析 → 列印報表」展示一頁式日報。

---

**常見提問**

| 問題 | 回答重點 |
| --- | --- |
| 手機關 Wi-Fi 怎麼辦？ | 那一區會少算，但入口人數是準的，k 會把整體拉回來；雷達也能確認有沒有人 |
| MAC 隨機化？ | 會多算，同樣由 k 修正；這也是一定要有入口紅外線當標準答案的原因 |
| 網路斷了會怎樣？ | 入口板子自己判斷閘門；今天的數字每 30 秒存進 NVS，斷電也不會歸零 |
| 為什麼用 Node-RED？ | 內建 Aedes broker、拖拉就能改規則，課堂上也看得到資料流 |
